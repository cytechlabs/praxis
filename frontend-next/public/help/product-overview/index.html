Product overview

Executive summary

Praxis is a self-hosted Linux fleet lifecycle control plane. It gives infrastructure, security, and operations teams one place to enroll Linux hosts, understand their state, control administrative access, manage packages and repository content, orchestrate patching, collect compliance evidence, govern remediation, and retain an audit trail of operator and system activity.

Praxis is designed for organizations that want to keep the policy authority and operational data inside their own environment. The control plane can reach hosts over SSH, using short-lived certificates signed through HashiCorp Vault, or use an optional thin agent for outbound-only connectivity. Operators work primarily in a web application, while the backend remains the sole authority for authorization, policy, orchestration, secrets access, and audit.

In practical terms, Praxis answers four recurring fleet-management questions:

  1. What is running? Inventory, host facts, installed packages, update state, lifecycle status, groups, baselines, and drift.
  2. Who can do what? Fleet-scoped roles, time-bound access, approvals, short-lived SSH identity, command policy, recordings, and audit events.
  3. How do we change it safely? Repository content, patch policies, staged rollout rings, maintenance windows, update plans, approvals, reboot policy, execution tracking, and rollback evaluation.
  4. Can we prove what happened? Compliance evidence, remediation history, package and fleet reports, session recordings, configuration audit, and exportable audit events.

Who Praxis is for

Praxis is intended for teams responsible for Linux servers across data centers, cloud networks, edge locations, restricted networks, or mixed environments. Its primary users include:

  • Infrastructure and platform teams managing operating-system inventory, packages, patching, maintenance windows, and fleet health.
  • Security operations teams controlling privileged access, command execution, credentials, SSH posture, and remediation activity.
  • Compliance and audit teams reviewing access history, system evidence, configuration state, approvals, changes, and exported audit records.
  • Organizations with disconnected environments that need to curate signed package content on a connected instance and transfer it into an air-gapped deployment.
  • Small and midsize teams that want a complete self-hosted control plane without requiring a SaaS management tier. The free edition supports up to 15 managed hosts and does not call home.

Typical use cases include maintaining a production Linux fleet, governing vendor or administrator access, rolling out security patches in stages, proving change control to an auditor, identifying end-of-life operating systems, standardizing repository configuration, and servicing isolated networks.

Product capabilities

Fleet enrollment, inventory, and lifecycle visibility

Praxis maintains a central record for every managed Linux system and the facts needed to operate it.

  • Register and enroll hosts through SSH or the optional agent workflow.
  • Collect distribution, release, kernel, architecture, package-manager, uptime, reboot-required, and other operating-system facts.
  • Inventory installed packages and available updates across the fleet.
  • Organize systems with static groups, tags, and fact-driven smart groups.
  • View fleet dashboards, individual system details, system status, and fleet health.
  • Compare systems, capture baselines, and identify drift from expected state.
  • Track distribution lifecycle and end-of-life status using shipped reference data.
  • Select auto, ssh, or agent as the non-interactive transport preference for an individual host.
  • Decommission systems without deleting their historical operational records.

This makes Praxis useful both as a day-to-day operations console and as a source of normalized fleet context for patch, compliance, and access decisions.

Identity, access, and privileged-session governance

Praxis brokers access to managed hosts instead of treating SSH credentials as uncontrolled shared configuration.

  • Authenticate with local accounts or bring an existing OIDC identity provider.
  • Map OIDC role claims to the built-in admin, maintainer, and auditor application roles.
  • Define fleet roles with allowed actions, operating-system groups, sudo policy, maximum session duration, idle timeout, and recording retention.
  • Scope access to fleets or system groups through bindings rather than granting universal host access.
  • Request, approve, reject, revoke, and expire just-in-time access.
  • Provision per-user Linux identities or use explicit role-account behavior while preserving the Praxis user identity in the certificate and audit record.
  • Require TOTP step-up authentication for privileged fleet roles.
  • Open interactive browser-based SSH terminals.
  • Track active sessions and retain searchable session recordings.
  • Transfer files through governed upload and download operations.
  • Review access history and the resulting authorization changes.

The paid edition adds session locks, session approval workflows, and formal access reviews. Interactive browser terminals use SSH in Praxis 1.0 even when the host uses the agent for non-interactive work; this preserves attributable Unix-user identity through a short-lived SSH certificate.

Secrets, SSH identity, and host trust

HashiCorp Vault is the custody boundary for credentials and certificate-authority material. The Praxis database stores metadata and references, not secret values.

  • Store and manage host credentials through Vault-backed records.
  • Use Praxis-managed Vault or connect an external Vault deployment.
  • Issue short-lived SSH user certificates whose lifetime is bounded by session policy.
  • Manage SSH certificate-authority state and rotation.
  • Establish host-key trust with a trust-on-first-use workflow and retain the resulting identity metadata.
  • Configure SSH connection behavior and security settings centrally.
  • Rotate authority state and invalidate pooled connections so future operations must obtain fresh identity.

These controls reduce dependence on long-lived shared keys and keep secret material outside the application database.

Command execution and control

Praxis provides governed remote command execution for both individual and fleet operations.

  • Run non-interactive commands on authorized hosts.
  • Define command whitelists and validation rules.
  • Reject or constrain commands that do not meet policy.
  • Preserve command history, target, actor, outcome, and result-processing data.
  • Require approval for sensitive commands and support multi-approval execution in the paid edition.
  • Review command metrics in the paid edition.
  • Use administrator bypasses where permitted while recording that the validation path was bypassed.

Command execution remains subject to backend authorization and audit regardless of whether the host operation travels over SSH or the optional agent.

Package inventory and update management

Praxis connects observed package state to operational update workflows.

  • Search for a package across the fleet.
  • Browse installed-package inventory per host and across hosts.
  • Identify available and security-relevant updates.
  • Track update history and repository status.
  • Ingest and associate patch advisories with affected systems.
  • Generate package-oriented operational reports.
  • Run package installation, removal, and upgrade operations through governed execution paths.

Package servicing is implemented for Debian-family apt systems and Enterprise Linux-family dnf systems. Detection of another package manager does not imply that Praxis can patch it; see Platform support.

Repository mirrors and content lifecycle

Praxis can curate the package content hosts consume instead of relying only on direct access to public upstream repositories.

  • Define and synchronize Debian and RPM repository mirrors.
  • Track synchronization runs, manifests, status, and retention metadata.
  • Schedule mirror work safely across workers and reserve minimum free disk space.
  • Sign repository content and distribute trust material.
  • Perform staged signing-key rotation with fingerprint checks.
  • Build content channels that select and optionally pin mirror states.
  • Compose channels into content profiles.
  • Assign one effective content profile to a host and explicitly apply the resulting repository configuration.
  • Serve mirror content to enrolled hosts with scoped credentials.
  • Browse mirror content and inspect individual synchronization runs.

Praxis 1.0 keeps one live materialized byte tree per mirror. Older run metadata and manifests can be retained, but arbitrary historical package bytes are not a snapshot archive. Retained air-gap bundle files are the supported mechanism for byte-exact historical content preservation.

Air-gapped content transfer

Praxis supports a complete disconnected content workflow between two control planes.

  1. A connected Praxis instance synchronizes mirrors and assembles selected content profiles into a bundle.
  2. The exporter signs a self-describing manifest and includes the selected repository bytes, channel/profile definitions, and mirror signing material.
  3. An operator transfers the bundle over approved physical or offline media.
  4. The disconnected Praxis instance verifies it against an exporter public key that the operator pinned out of band.
  5. Verified content is imported as an offline mirror that will not attempt an upstream synchronization.

The importer validates paths, signatures, hashes, declared content, package family, and trust. It does not trust a signing key merely because that key was included in the bundle. Full and delta bundle workflows are available, subject to the documented snapshot and parent-bundle constraints.

Patch policy, rollout, and rollback

Praxis separates reusable rollout policy from a particular patch run. This allows teams to express how updates should move through the fleet and then retain each execution as a distinct operational record.

  • Define patch policies independently of hosts and individual update plans.
  • Assign policies to systems and resolve the effective policy for a host.
  • Create rollout rings for staged deployments such as canary, early adopter, and broad production phases.
  • Build update plans against explicit package and host scope.
  • Perform preflight evaluation and capture plan-time state.
  • Require scoped approvals before execution.
  • Respect maintenance windows and schedule work.
  • Control reboot behavior and track reboot-related state.
  • Execute and monitor work per host rather than treating a fleet rollout as one opaque action.
  • Evaluate whether rollback is feasible and dispatch supported rollback actions.
  • Retain advisories, plan history, execution outcomes, and rollback records.

This model is intended to make a patch rollout explainable before, during, and after the change—not simply provide a fleet-wide “update all” button.

Jobs and maintenance operations

Praxis includes a general operational job layer for recurring and asynchronous fleet work.

  • View active, scheduled, completed, and failed jobs.
  • Create reusable job templates.
  • Schedule jobs and inspect job history.
  • Define maintenance windows that constrain disruptive activity.
  • Track failures for follow-up and preserve operational outcomes.
  • Review fleet operations history across package, patch, command, and lifecycle activity.

Compliance evidence and remediation

Praxis evaluates operator-defined compliance policy against host evidence and connects failed findings to a governed remediation lifecycle.

  • Create versioned compliance policies and checks.
  • Install a starter policy pack to bootstrap common checks.
  • Evaluate policies per host and preserve the evidence, verdict, severity, and evaluation-run identity.
  • View fleet and per-system compliance status.
  • Export evidence; bulk evidence exports are a paid entitlement.
  • Open a remediation request from a failing finding.
  • Enforce separation of duties between requester and approver.
  • Build a structured remediation plan, detect when its source check has changed, acknowledge the plan, and preserve superseded versions.
  • Expose a fail-closed readiness gate before execution.
  • Dispatch approved package install, remove, or upgrade remediation plans through the governed patch transport, with durable attempt state and audit events.
  • Review per-request execution rollups and export remediation execution history.

Automated remediation is deliberately narrower than evidence collection. Package-oriented plans can execute when every gate passes. File-content, command-output, fact, unknown, or otherwise underspecified findings require operator review because Praxis does not invent the desired content or change.

Praxis produces evidence and change-control history; it does not attest that an organization is compliant. The supplied evidence map helps relate Praxis events to SOC 2, PCI DSS, and HIPAA discussions, but certification remains the responsibility of the organization and its auditor.

Monitoring, reporting, notifications, and audit

Operational and security activity is available through dashboards and durable records.

  • View system status, comparisons, baselines, and drift.
  • Browse an activity feed and fleet analytics.
  • Review package reports, fleet-operations history, and configuration audit.
  • Configure alerts and user notification preferences.
  • Inspect a stable audit-event envelope containing actor, source, target, action, outcome, timestamp, and contextual identifiers.
  • Record session, command, file-transfer, authorization, authentication, Vault, PKI, content, patch, compliance, and remediation events.
  • Deliver audit events to HTTP, RFC 5424 syslog, or file sinks.
  • Use event UUIDs to deduplicate at-least-once external delivery.
  • Export records for operational review and audit evidence.

Audit events remain in the application database until the operator removes them; Praxis 1.0 does not apply an automatic in-app retention window. External sinks should be used when immutable or policy-specific retention is required.

How Praxis works

Praxis uses a deliberately centralized policy model:

The browser talks to the frontend, which proxies application requests to the backend. The backend is the only application tier that accesses PostgreSQL, Vault, agent coordination, mirror storage, or managed hosts. This keeps authentication, authorization, lifecycle policy, and audit decisions in one place.

Host transport choices

SSH is the default compatibility path. It supports facts, commands, file operations, package work, and attributable interactive sessions. Vault-backed short-lived certificates can replace persistent user private keys for session identity.

The thin agent is optional. It is useful when inbound SSH from the control plane is undesirable or impossible. The agent opens an outbound mTLS WebSocket to the broker and exposes bounded primitives for command execution, PTY data, file operations, facts, and heartbeat. It does not own policy or package semantics; the backend still decides what may run and records the operation.

Security model

Praxis is built around several clear trust boundaries:

  • The backend is the policy authority and centrally enforces a JWT authentication floor on non-public API routes.
  • Fleet-scoped authorization and application roles limit who may view, approve, or perform operations.
  • Vault holds credentials, TOTP material, and certificate-authority secrets; PostgreSQL holds application metadata and lifecycle records.
  • SSH user certificates and agent certificates are short-lived and bound to authoritative status checks.
  • Agent identity uses mTLS, certificate fingerprint validation, bounded operation channels, nonces, and explicit capability negotiation.
  • Air-gap imports require an independently pinned exporter key and fail closed on signature, hash, path, or content inconsistencies.
  • Audit records make privileged actions and policy decisions attributable.
  • Production startup validates security-sensitive environment configuration and refuses known-unsafe worker settings unless explicitly overridden.

Praxis does not provide CRL or OCSP services in 1.0. Certificate containment uses short lifetimes, CA/status changes, broker-side blocklisting for agents, and connection invalidation. Disk, volume, and database encryption at rest remain an infrastructure responsibility.

Deployment and operations

Praxis is distributed as container images and is operated with Docker Compose. The main services are the Next.js frontend, FastAPI backend, PostgreSQL, Vault, and monitoring/backup support services.

Supported deployment patterns include:

  • A bundled single-node deployment with PostgreSQL and Vault in the Compose stack.
  • A deployment using external PostgreSQL and external Vault services.
  • Either model behind a TLS-terminating Caddy reverse proxy.
  • A fully offline deployment built from local artifacts and supplied through the signed air-gap content workflow.

Production releases include versioned backend and frontend images. The release process produces CycloneDX 1.6 software bills of materials, scans images with Trivy, and blocks critical known vulnerabilities in CI.

Praxis 1.0 supports a single backend worker while interactive SSH sessions are enabled because live terminal state is process-local. Horizontal backend scale, Docker Swarm, and multi-worker interactive sessions are not supported production topologies in this release. Operators are responsible for TLS, infrastructure hardening, database and Vault durability, backup verification, storage sizing, and external retention policy.

Editions

Praxis follows an open-core model. The free edition is a complete self-hosted fleet control plane and runs without a license, external licensing service, or call-home mechanism.

Free edition

The free edition supports up to 15 managed hosts and includes the operational core: unlimited users, OIDC, recordings, fleet inventory and grouping, Vault and SSH security, access requests, command execution and policy, package management, patching, repository content, air-gap transfer, jobs, monitoring, compliance, remediation, audit, and reporting.

Paid edition

The paid edition adds scale and governance:

  • Managed hosts above the free cap.
  • Session locks and session approvals.
  • Formal access reviews.
  • Command approval queue, multi-approval execution, and command metrics.
  • Bulk compliance/evidence exports.
  • Scheduled and recurring report exports.

Licenses are signed, offline-verifiable tokens bound to a stable installation ID. Applying a license unlocks entitlements in the same deployment. An expired or invalid license does not delete or disable existing hosts; it blocks additional registrations beyond the effective cap and exposes a grace period for an over-cap deployment.

Platform support

The official managed-host boundary for Praxis 1.0 is:

AreaSupported
Architecturesx86_64/amd64 and aarch64/arm64
Debian familyUbuntu LTS 22.04, 24.04, 26.04; Debian 13
Enterprise Linux familyRHEL 8–10, Rocky Linux 8–10, AlmaLinux 8–10
Package servicingapt/Deb packages and dnf/RPM packages

Some older or adjacent distributions are best-effort, including Ubuntu 20.04, Debian 10–12, EL7, Fedora, Oracle Linux, and Amazon Linux. zypper, pacman, and apk hosts may be detected and inventoried, but patching, rollback, mirror trust, and content-profile application are unsupported. EL7 patch execution is best-effort because the current Enterprise Linux path invokes dnf, and reboot detection underreports Enterprise Linux systems that require needs-restarting rather than a Debian-style marker file.

See the Linux support matrix for the release-by-release boundary and validation caveats.

Product boundaries and known limitations

Praxis is intentionally not all of the following:

  • Not a compliance certification service. It collects evidence and supports governance workflows; it does not attest compliance.
  • Not endpoint DLP. It does not classify or prevent arbitrary data movement outside the operations it brokers.
  • Not a network-segmentation platform. Network policy beyond the control plane and managed-host connectivity remains external.
  • Not an encryption-at-rest provider. Operators must secure the PostgreSQL, Vault, mirror, backup, and volume storage layers.
  • Not a universal Linux package manager. Full lifecycle servicing is limited to the supported APT and DNF families.
  • Not an arbitrary historical repository archive. Mirror history retains metadata; retain exported bundles when historical bytes are required.
  • Not horizontally scalable for interactive sessions in 1.0. The supported interactive deployment uses a single backend worker.
  • Not fully automatic remediation for every finding. Only safe, sufficiently-specified package remediation plans can use the automated governed execution path.
  • Not an automatic audit-retention engine. In-app events are not pruned by a built-in retention policy.

These are explicit product boundaries so that teams can pair Praxis with the appropriate storage, network, DLP, SIEM, identity-provider, and compliance controls.

The value of Praxis

Linux operations are often split across an asset inventory, SSH bastions, credential stores, package scripts, patch schedulers, compliance scanners, and hand-built audit exports. Praxis brings those workflows into one policy and evidence model. A host discovered in inventory is the same host targeted by an access grant, assigned repository content, placed into a patch ring, evaluated against compliance policy, and represented in the audit trail.

That continuity is the central product benefit: teams can move from observation to authorized change to evidence without losing host identity, operator identity, policy context, or execution history between tools.
